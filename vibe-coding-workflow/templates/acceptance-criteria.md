## 1. 功能验收

### 1.1 核心功能验收

验证模块的核心功能是否按照 plan.md 要求正常工作。

- [ ] 📋 <验收项 1 描述> — 验证方式：<如：执行 API 调用，检查返回结果>
- [ ] 📋 <验收项 2 描述> — 验证方式：<如：登录后访问受保护资源>
- [ ] 📋 <验收项 3 描述> — 验证方式：<如：创建资源后查询确认已入库>

### 1.2 边界条件验收

验证模块在边界值和极限情况下的表现。

- [ ] 🔲 空值 / null 处理：输入为空时返回明确的错误提示
- [ ] 🔲 空字符串处理：输入为空字符串时返回明确的错误提示
- [ ] 🔲 最大长度限制：输入超过最大长度时正确拒绝
- [ ] 🔲 最小长度限制：输入不足最小长度时正确拒绝
- [ ] 🔲 最大值/最小值：数值超出范围时正确拒绝
- [ ] 🔲 特殊字符处理：输入含特殊字符（`<`、`>`、`&`、`"`、`'`、SQL 关键字）时不出现异常

### 1.3 异常场景验收

验证模块在异常情况下的行为是否符合预期。

- [ ] ⚡ 数据库不可用：返回 500 错误，不泄露数据库信息
- [ ] ⚡ 外部服务超时（如 AI API）：30 秒超时后返回 503，日志记录完整
- [ ] ⚡ 外部服务返回错误：正确处理并返回友好提示
- [ ] ⚡ 并发请求：同时发起多个请求，数据一致性正确（幂等性）
- [ ] ⚡ 重复提交：相同请求提交两次，不会重复创建数据
- [ ] ⚡ 数据不存在：查询不存在的资源返回 404

## 2. 接口验收

### 2.1 返回格式验收

验证所有 API 接口的返回格式是否符合统一规范。

- [ ] 📦 成功响应格式为 `{"code": 0, "msg": "success", "data": {...}, "timestamp": ..., "request_id": "..."}`
- [ ] 📦 失败响应格式为 `{"code": X, "msg": "...", "data": {.../null}, "timestamp": ..., "request_id": "..."}`
- [ ] 📦 分页响应 data 包含 `items` 和 `pagination` 结构
- [ ] 📦 所有响应包含 `timestamp` 字段（毫秒时间戳）
- [ ] 📦 所有响应包含 `request_id` 字段（UUID v4 格式）
- [ ] 📦 响应 Content-Type 为 `application/json; charset=UTF-8`

### 2.2 错误处理验收

验证错误响应的准确性和友好性。

- [ ] 📦 参数校验失败 → 返回 400，msg 包含具体字段和原因
- [ ] 📦 资源不存在 → 返回 404，msg 提示明确
- [ ] 📦 认证失败 → 返回 401，msg 提示需要登录
- [ ] 📦 权限不足 → 返回 403，msg 提示无权限
- [ ] 📦 资源冲突 → 返回 409，msg 说明冲突原因
- [ ] 📦 服务器内部错误 → 返回 500，msg 为通用提示（不泄露堆栈信息）
- [ ] 📦 服务不可用 → 返回 503，msg 说明依赖服务问题

### 2.3 端点命名验收

- [ ] 📦 路径使用 kebab-case，资源名使用名词复数
- [ ] 📦 查询参数使用 snake_case
- [ ] 📦 HTTP 方法使用正确（GET/POST/PUT/DELETE 语义正确）

## 3. 代码质量验收

### 3.1 注释覆盖率

- [ ] 💻 所有 public 方法有 Javadoc/Docstring 注释
- [ ] 💻 复杂业务逻辑（≥ 10 行）有行内注释说明
- [ ] 💻 魔法数字已定义为有意义的常量并添加注释
- [ ] 💻 TODO / FIXME 标记附带说明
- [ ] 💻 注释内容有实际意义，不冗余

### 3.2 命名规范

- [ ] 💻 类名 / 方法名 / 变量名符合 CLAUDE.md 命名规范
- [ ] 💻 文件名符合规范（snake_case 或 kebab-case）
- [ ] 💻 没有无意义的命名（如 `a`、`temp`、`data`、`handle`）
- [ ] 💻 没有拼音命名

### 3.3 分层架构

- [ ] 💻 Controller 层不包含业务逻辑
- [ ] 💻 Service 层不直接处理 HTTP 请求/响应
- [ ] 💻 Repository 层不包含业务逻辑，不处理事务
- [ ] 💻 不存在跨层调用（Controller → Repository）
- [ ] 💻 不存在反向依赖（Repository → Service → Controller）
- [ ] 💻 Entity 未暴露到 Controller 层

### 3.4 代码长度

- [ ] 💻 单个方法 ≤ 50 行（默认，特殊情况见 plan.md）
- [ ] 💻 单个类 ≤ 500 行（默认，特殊情况见 plan.md）
- [ ] 💻 本模块新增功能代码 ≤ 200 行（默认，不含注释/docstring/测试；若 plan.md 已明确采用含注释/测试口径并预估，则自动豁免）

### 3.5 编译检查

- [ ] 💻 代码通过编译，无编译错误
- [ ] 💻 无 linter 警告（或所有警告已处理）
- [ ] 💻 无 import 未使用的依赖

## 4. 测试验收

### 4.1 单元测试

- [ ] 🧪 Service 层核心方法有单元测试覆盖
- [ ] 🧪 单元测试覆盖正常路径（Happy Path）
- [ ] 🧪 单元测试覆盖边界条件（空值、极值、特殊字符）
- [ ] 🧪 单元测试覆盖异常场景（依赖失败、数据不存在）
- [ ] 🧪 单元测试代码行覆盖率 ≥ 80%（默认，按 plan.md 约定执行）

### 4.2 集成测试

- [ ] 🧪 Controller 层接口有集成测试覆盖
- [ ] 🧪 集成测试覆盖成功场景（200 响应）
- [ ] 🧪 集成测试覆盖错误场景（400/404/409/500 响应）
- [ ] 🧪 集成测试验证了数据库操作的正确性
- [ ] 🧪 集成测试代码覆盖率 ≥ 60%（默认，按 plan.md 约定执行）

### 4.3 回归测试

- [ ] 🧪 运行全部已有测试，确保无失败用例
- [ ] 🧪 已有功能的行为没有被改变（除非 plan.md 明确要求）

### 4.4 测试命令

```bash

./gradlew test --tests "com.xxx.service.XxxServiceTest"

./gradlew test --tests "com.xxx.controller.XxxControllerTest"

# 运行回归测试
./gradlew test

# 运行真实环境冒烟（涉及 DB / 外部依赖时）

# 生成覆盖率报告

```
