## 一、架构检查

### 1.1 分层是否正确

- [ ] ❌/✅ Controller 层：仅负责参数校验和格式转换，不包含业务逻辑
- [ ] ❌/✅ Service 层：包含核心业务逻辑，不直接处理 HTTP 请求/响应
- [ ] ❌/✅ Repository 层：仅负责数据 CRUD，不包含业务逻辑
- [ ] ❌/✅ AI 集成层：代码放置在 `src/main/ai/` 目录下

### 1.2 依赖方向是否正确

- [ ] ❌/✅ 是否存在跨层调用（Controller 直接调用 Repository）
- [ ] ❌/✅ 是否存在反向依赖（Repository 依赖 Service，Service 依赖 Controller）
- [ ] ❌/✅ Service 之间的互相调用是否形成循环依赖
- [ ] ❌/✅ DTO 使用是否合规（Entity 未暴露到 Controller 层）

### 1.3 模块拆分是否合理

- [ ] ❌/✅ 单个类代码量 ≤ 500 行
- [ ] ❌/✅ 单个方法代码量 ≤ 50 行
- [ ] ❌/✅ 本模块新增代码量 ≤ 200 行
- [ ] ❌/✅ 类职责单一，无明显的大杂烩类

---

## 二、编码规范检查

### 2.1 命名规范

**Java 项目**：
- [ ] ❌/✅ 类名使用 PascalCase
- [ ] ❌/✅ 方法名使用 camelCase
- [ ] ❌/✅ 变量名使用 camelCase
- [ ] ❌/✅ 常量使用 UPPER_SNAKE_CASE
- [ ] ❌/✅ 包名全小写，点分隔

**Python 项目**：
- [ ] ❌/✅ 类名使用 PascalCase
- [ ] ❌/✅ 函数/方法名使用 snake_case
- [ ] ❌/✅ 变量名使用 snake_case
- [ ] ❌/✅ 常量使用 UPPER_SNAKE_CASE

**通用**：
- [ ] ❌/✅ 文件名使用 snake_case（与规范一致）
- [ ] ❌/✅ 数据库表名/字段名使用 snake_case
- [ ] ❌/✅ 变量名有意义，无 `a`、`temp`、`data` 等无意义命名
- [ ] ❌/✅ 没有拼音命名

### 2.2 注释覆盖

- [ ] ❌/✅ 所有 public 方法有 Javadoc / Docstring 注释
- [ ] ❌/✅ 复杂业务逻辑（≥ 10 行）有行内注释
- [ ] ❌/✅ 魔法数字已定义常量并添加注释
- [ ] ❌/✅ TODO / FIXME / HACK 标记附带说明
- [ ] ❌/✅ 注释内容准确，非无用注释（如 `// set name`）

### 2.3 异常处理

- [ ] ❌/✅ 没有空 catch 块（吞掉异常）
- [ ] ❌/✅ Controller 层没有捕获异常后不做处理
- [ ] ❌/✅ 所有业务异常继承统一的 BusinessException
- [ ] ❌/✅ 异常日志包含完整堆栈信息
- [ ] ❌/✅ try-catch 范围合理，不过大也不过小

### 2.4 日志规范

- [ ] ❌/✅ 关键业务操作有 INFO 级别日志
- [ ] ❌/✅ 日志包含入参摘要 + 结果 + 耗时
- [ ] ❌/✅ 异常日志包含 request_id 用于链路追踪
- [ ] ❌/✅ 没有输出用户敏感信息（密码、手机号、身份证号）
- [ ] ❌/✅ 日志级别使用恰当（ERROR / WARN / INFO / DEBUG）

---

## 三、接口规范检查

### 3.1 返回格式

- [ ] ❌/✅ 所有 API 返回统一格式 `{code, msg, data, timestamp, request_id}`
- [ ] ❌/✅ 成功时 code 为 0
- [ ] ❌/✅ 失败时 code 为对应的 HTTP 状态码
- [ ] ❌/✅ 分页接口使用标准分页结构 `{items, pagination: {page, page_size, total, total_pages}}`
- [ ] ❌/✅ 错误响应包含有意义的 `msg` 和 `data` 详情

### 3.2 API 端点命名

- [ ] ❌/✅ 路径使用 kebab-case
- [ ] ❌/✅ 资源名使用名词复数
- [ ] ❌/✅ 查询参数使用 snake_case
- [ ] ❌/✅ 请求/响应体字段使用 snake_case
- [ ] ❌/✅ HTTP 方法使用正确（GET 查询、POST 创建、PUT 更新、DELETE 删除）

### 3.3 参数校验

- [ ] ❌/✅ 请求体字段有校验注解（@NotNull、@NotBlank、@Size 等）
- [ ] ❌/✅ 路径参数有校验（@PathVariable 有对应验证）
- [ ] ❌/✅ 查询参数有默认值和范围限制
- [ ] ❌/✅ 校验错误返回明确的字段级错误信息

---

## 四、安全检查

### 4.1 注入防护

- [ ] ❌/✅ SQL 查询使用参数化查询（无字符串拼接 SQL）
- [ ] ❌/✅ 用户输入在输出时已转义 HTML 特殊字符（防 XSS）
- [ ] ❌/✅ 没有直接将用户输入拼接到命令执行中

### 4.2 认证与授权

- [ ] ❌/✅ 需要认证的接口已标注认证要求
- [ ] ❌/✅ 状态变更请求已验证 CSRF Token
- [ ] ❌/✅ 接口没有越权风险（用户只能操作自己的数据）

### 4.3 敏感信息保护

- [ ] ❌/✅ 密码使用 BCrypt / Argon2 加密存储（禁止明文）
- [ ] ❌/✅ API Key / 密钥使用环境变量或密钥管理服务（禁止硬编码）
- [ ] ❌/✅ 日志中没有输出敏感信息
- [ ] ❌/✅ 响应体中不返回密码、密钥等敏感字段

### 4.4 依赖安全

- [ ] ❌/✅ 新增依赖已经安全审计（无已知漏洞）
- [ ] ❌/✅ 依赖版本不是过期的快照版本

---

## 五、性能检查

### 5.1 数据库操作

- [ ] ❌/✅ 没有 N+1 查询问题（循环内逐条查询数据库）
- [ ] ❌/✅ 批量操作使用批量接口（batch insert / update）
- [ ] ❌/✅ 查询已添加必要的数据库索引
- [ ] ❌/✅ 没有 SELECT * 查询，只查询需要的字段

### 5.2 IO 操作

- [ ] ❌/✅ 没有在循环内进行文件 / 网络 IO 操作
- [ ] ❌/✅ 外部服务调用已设置超时时间（默认 30 秒）
- [ ] ❌/✅ 外部服务调用有重试机制（最多 3 次）

### 5.3 缓存使用

- [ ] ❌/✅ 高频读取数据是否考虑缓存（Redis）
- [ ] ❌/✅ 缓存的使用是否有过期策略
